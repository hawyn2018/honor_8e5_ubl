# Rebuilding the OTA module

`build_module.py` performs local compilation and packaging only. It does not access a phone, install a module, run an injected process or download dependencies.

Use Python 3.12+, JDK 17+ (the current build uses JDK 21), Android SDK platform 37 and its D8 build tool, and Node.js 18+. Set `JAVA_HOME`, `ANDROID_SDK_ROOT` and `PATH`, or pass `--java-home`, `--sdk` and `--node`. Current-machine fallback paths exist for the known local toolchain; explicit arguments work on other machines.

## First local build

Supply `--vendor` with the verified dependencies directory. It contains:

- `frida-inject-17.25.0-android-arm64.xz` and `download-manifest.json`.
- Optionally the decompressed `frida-inject`, which is verified separately if present.
- `js/package.json`, `js/package-lock.json` and a complete `js/node_modules` generated by `npm ci --ignore-scripts --no-audit --no-fund`.

Pinned JS versions are `frida-java-bridge 7.0.13`, `esbuild 0.28.2` and `buffer 6.0.3`. npm verifies package tarball SRI during `npm ci`. The builder validates versions and locks, records the installed file hashes at this checkpoint, and requires those hashes on subsequent builds for the same platform. It does not vendor `node_modules` or execute package installation scripts.

Pass `--jadx` with the local `jadx-1.5.6-all.jar` on the first build. The script extracts DEXlib2, its utility classes, Guava and annotation dependencies, then follows class constant-pool references to include additional classes from that JAR as needed. It validates ZIP CRCs and records the source JAR SHA-256, class count and generated JAR SHA-256.

Example:

```powershell
python .\ota-module\build_module.py --vendor D:\ai_work\honorubl\analysis\hnubl-2.7.3-ota-module-20261101\vendor --jadx D:\ai_work\honorubl\analysis\tools\jadx\lib\jadx-1.5.6-all.jar --out D:\ai_work\honorubl\analysis\hnubl-2.7.3-ota-module-20261101\module-build
```

## Source-package rebuild

Successful builds store the compressed Frida runtime, its metadata, `jvm-deps.jar`, `dependency-lock.json`, and the JS package files under `ota-module/vendor`. The source package needs these files, the Java/JS/module source, and third-party license notices. Build folders, logs, private keys and `node_modules` should remain excluded.

Run standard npm in `ota-module/vendor/js` first, then build without `--jadx` or `--vendor`:

```powershell
Set-Location .\ota-module\vendor\js
npm ci --ignore-scripts --no-audit --no-fund
Set-Location ..\..\..
python .\ota-module\build_module.py
```

The existing JVM and JS dependency lock is checked before using the vendored inputs. A changed dependency stops the build rather than silently replacing the lock. Rebuilding on a different OS revalidates the same JS package lock and records that platform's installed package hashes, since esbuild's native executable is platform-specific.

## KSU-provider runtime variant

The original Frida XZ and download manifest remain unchanged. The builder derives
the hnubl runtime with the pure-standard-library recipe in `runtime-patches/`.
The exact upstream ELF hash, initializer/label structure and output hash must
match; any mismatch stops the build. The derived runtime skips Frida's automatic
whole-policy export/reload and reuses the provider's existing `ksu_file` memfd
context. It does not fall back to the original policy-rewriting initializer.
See `runtime-patches/README.md` for scope, required existing provider permissions,
source changes, all pinned hashes and offline positive/negative guard tests.

Runtime provenance is included as `runtimeVariant` in the build manifest and
dependency lock, as `runtime-variant.json` in staging, and as
`licenses/frida-runtime-variant.json` in the module ZIP. All four records agree,
and the payload hash manifest binds the derived executable.

## Outputs and recovery after interruption

The default working output is `ota-module/build`. `--out` can select an external analysis directory; it cannot point into Java/JS/module source folders. Every run uses a new staging directory and keeps failed logs for inspection. No recursive deletion is used.

The script compiles all broker/controller/discovery Java sources with `javac --release 17`, packages the program classes, runs D8 with `--min-api 28`, and creates `broker.jar` containing all generated DEX files. The hook is bundled as a neutral IIFE with esbuild and a Buffer injection shim. Module installation files, `broker.jar`, `agent.bundle.js`, the ARM64 executable and a payload hash manifest form the reproducible ZIP.

Successful final assets are written atomically to:

- `app/src/main/assets/modules/hnubl-ota.zip`
- `app/src/main/assets/modules/hnubl-ota.sha256`

ZIP timestamps and modes are fixed. The working `build-manifest.json` is `building` during execution, `failed` after any error, and `complete` only after source/dependency stability checks and final output hashing. It includes all source hashes, dependency lock hash, actual tool binary hashes, module and payload hashes, and the staging path. The app/release build should require a `complete` manifest and matching asset SHA before publishing.

After a computer restart, rerun the entire command. A truncated dependency or altered source fails its checksum/CRC/snapshot checks. A partially replaced asset pair cannot pass the module SHA check; the next successful build replaces both. Final versioned APK/source archives are published separately by the parent release process and are not overwritten by this script.
