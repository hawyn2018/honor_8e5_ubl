# 2.9.1：更新模块就绪、重启保护与延迟槽位激活

应用与内置 OTA 模块均为 2.9.1 / versionCode 89，基于已发布的 2.9.0。

## 原问题

现场旧常驻服务是 UID 0，但继承了 hnubl 的隔离挂载视图，无法访问软件更新的 DE 数据目录。OTA socket 创建持续报 ENOENT。软件更新中的必需初始化连接失败后，控制器执行 force-stop；已有六次同 PID 的初始化失败与退出记录对应，另一次退出没有对应的 agent 事件。App 还只接受运行中 hook_ready，未接受控制器与通信已就绪、等待软件更新启动的合法空闲状态。

## 修复

服务通过验证并固定系统根目录 FD，逐层打开 PackageManager 返回的目标目录。OTA-only listener 可以热替换，并与旧常驻 Root 服务共用原有 marker 事务，不关闭正在承载安装命令的 Root 连接。Root 客户端的 DE 路径和认证合同保留。

App 核对本次激活身份及真实布尔状态，分别显示运行就绪或空闲等待；安装阶段的日志实时进入界面。软件更新的手动、自动重启及倒计时保护是必需部分。全量包选择、设置覆盖、版本过滤等附加功能缺失或执行失败时记录 warning，继续原更新处理。运行期 warning 同时尽力写入 logcat。

## 原生延期激活

原生脚本只附着经进程、可执行文件和启动身份核对的 update_engine；按当前 ELF 的函数名、ABI、函数范围及实际调用关系定位，不包含设备或版本到地址的映射。

保持原 payload 参数、多包 manifest 合并、验签、快照 FinishUpdate 和原完成码。只有成功 CompletePostinstall 上下文、真实 FinishUpdate=true、直接父调用范围同时成立，且 root 已耐久保存本周期目标槽并回执，才暂缓 SetActiveBootSlot。原生 TerminateUpdateAndNotify 返回成功后记录完成；其他结果保持失败语义。

BEGIN 开始新周期并重置旧许可；普通完成 RESET 不清除延期计划。用户点击原更新应用的手动重启入口时，先核对 freeotaok=1、本次启动身份及已完成的延期计划，再通过当前系统的 typed setSlot 接口执行真实激活。只有得到真实成功并保存提交回执后，才消费许可并继续原重启入口。切槽结果不确定时保留证据，不自动重放 HAL。

可选原生能力未定位或未建立通信时记录原因并保持原更新行为，关键重启门继续保护。已经收到耐久 DEFER 的计划不以可选回退方式放行；未完成或不确定计划保持关闭。计划在软件更新进程重开后仍保留，跨设备重启的旧计划不被盲目激活。

## 验证边界

验收记录区分主机状态机与变形测试、隔离 ARM64 样本的实际拦截，以及软件更新界面的进程存活与就绪检查。没有以 mock 的成功替代完整真实 OTA，也没有在验收中执行真实系统更新、切槽或重启。
