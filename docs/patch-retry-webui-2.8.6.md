# 2.8.6 修补失败引导与 WebUI 响应

解锁三种模式和完整 OTA 的实际非内置镜像修补失败时，任务暂停并等待用户选择。解锁侧读取预览和导出操作包中实际进行修补时同样适用。弹窗按操作显示：

> 修补选定镜像失败，是否使用应用内置镜像修补，并继续完成后续解锁流程？

OTA 页面使用“OTA流程”。选择“是”后，仅替换 efisp 的生成来源为应用内置 ABL，沿用本次假回锁/仅解锁修补模式、独立选择的 ABL 刷写文件和目标范围，重新修补、定制文字、校验成品，再进入原后续流程。选择“否”或返回会停止，日志为“选定镜像修补失败，用户选择停止解锁流程”或“选定镜像修补失败，用户选择停止OTA流程”。

OTA 页的“仅刷写 efisp”和“导出 efisp”不弹确认：实际修补失败时停止，在导出按钮下显示对应动作的红字“刷写efisp失败，可选择内置ABL修补选项后重试刷写流程”或“导出efisp失败，可选择内置ABL修补选项后重试导出流程”。提示复用现有单独更新红字组件，字号、行距及上下间距一致；手动改变来源或开始下一次任务后清空。真实读写/文档提供者错误不错误标为修补失败。

普通修补异常适用此引导，内置 ABL 失败只传播一次。来源提取/上传/备份/刷写错误不伪装修补异常，也不通过重试重新运行已开始的写入事务。直接刷入上传 efisp 没有初次修补步骤；如果后续既有 OTA 成品策略要求从当前槽重新生成，该次非内置修补失败同样询问。取消、服务销毁、中断和内存耗尽不自动转为重试。

确认等待属于进程级任务，不属于某一 Activity：页面重建仍显示等待，唯一请求编号拦截旧/重复回答，服务结束会取消其等待。用户没有确认时不会默认采用内置镜像。

解锁来源记录继续用 EFI_SOURCE 绑定原请求；确认回退成功后增加 PATCH_RETRY_SOURCE=BUILTIN_ABL，实际成品来源为内置完整摘要，并清除原设备 SOURCE_SLOT/DEVICE/MM/CAPACITY 身份。两个执行后端识别该标记并核对合法来源和内置摘要，导出仍与原请求匹配。该字段与已移除的防回滚准入无关。

OTA 原有计数读取与前级备份/对拷策略保持；成品策略内当前槽修补失败也接入同一显式确认，确认内置后按原最后内置候选规则采用。低层 ota-device.sh 的 by-name、setrw、dd、回读、范围检查和无自动切槽/重启流程保持。

WebUI 调整交互状态与绘制时机：点击选择立即反馈，保存/应用期间显示待确认，失败恢复已确认值；已收到就绪证据时及时完成，尚未就绪才轮询。模块设置的持久化和激活协议继续由现有控制器负责，前端不提前宣布保存或生效。

应用与内置模块为 2.8.6 / versionCode 79。修补核心、KBL、原有镜像、提权利用与许可证未因本次流程更新而修改。
